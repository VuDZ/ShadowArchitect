# B01. Исследовать идентичность исходного Blueprint

**Зависимости** — можно начинать с 0.1.1.

## Цель

Определить, как надёжно сопоставить план с исходным Blueprint. Зафиксировать правила для старых планов.

## С чего начать

В 0.1.1 `BlueprintId` содержит имя, а GUID относится к размещению. Для реального строительства нужен признак того, что найден именно сохранённый источник. [Захват геометрии](../../../../src/ShadowArchitect/Source/ShadowArchitect/Private/ShadowCapture.cpp) · [Данные снимка](../../../../src/ShadowArchitect/Source/ShadowArchitect/Private/ShadowPlan.h) · [Протокол совместимости и запуск SaveCheck](../../../save-compatibility.md)

## Работа

1. На одноразовых файлах A и B одинакового габарита с разным содержимым сравните доступные поля дескриптора и проверяемые признаки содержимого. Отметьте момент получения признака при захвате и при поиске.
2. Зафиксируйте правила решения для исходника без изменений, переименования, удаления и подмены под прежним именем. Рассмотрите старый снимок, у которого нового признака нет.

## Независимая проверка

- [x] Для каждого случая приведите имя, проверяемый признак и ожидаемый результат «найден», «отсутствует» или «неоднозначен/изменён». Обоснуйте поведение при переименовании.
- [x] Правило блокирует строительство при подмене и недостатке данных. Отдельная проверка в игре подтвердила видимость старых проекций во всех состояниях библиотеки. Исполнение правила в игре проверяется в B02.

## Результаты опытов

23 ноября 2026 года, ревизия `1676a7e`. Скопировали пары `.sbp` и `.sbpcfg` двух игровых чертежей в отдельные тестовые библиотеки. `QA_A` содержит два сборщика кабелей, `QA_B` — два сборщика медных листов. У обеих копий одинаковый двоичный заголовок до первого блока zlib, включая размеры дизайнера 4×4×4, стоимость и рецепты строительства. [Проба таблицы акторов](../../../../scripts/probe_blueprint.py) прочитала те же восемь классов и поз, в том же порядке. Различается содержимое сериализованного блока объектов. Размеры целых файлов составили 4079 и 4073 байта.

- **A** — BLAKE3 `971cc42d49480aadd0820ebfee8d07f77cfd66e5c6db800a4cafa553481b8fb1`.
- **B** — BLAKE3 `df179d8628c59d8951abe58e9ddcafd631ac2f5d681562cd2a8a810143fa032b`.

В каждом опыте исходное имя плана — `QA_A`. Результат в правом столбце получен сравнением файлов в одноразовой библиотеке по правилу B02. Для матрицы нужны две указанные копии либо два своих файла одинакового размера дизайнера с разным содержимым. Хешируйте целые файлы `.sbp` и при переименовании переносите обе части пары.

| Опыт | Имена в библиотеке | Сохранённый → наблюдаемый отпечаток | Решение |
|---|---|---|---|
| Без изменений | `QA_A` | A → A | Найден |
| Переименование пары | `QA_A_renamed` | A → A | Найден под новым именем |
| Удаление | нет | A → нет файла | Отсутствует |
| Подмена | `QA_A` | A → B | Изменён |
| Две одинаковые копии | `QA_A`, `QA_A_renamed` | A → A, A | Неоднозначен |
| Старая запись | `QA_A` | нет → A | Недостаточно данных |

Каждое состояние библиотеки загрузили в отдельном процессе Satisfactory Steam Shipping `rel-main-1.2.6` CL `520140`, SML `3.12.1`, Shadow Architect `0.1.2`. Входной тестовый слот `SAQ_BASE_01`, без выходного слота. SaveCheck перечислил указанные имена, обе записи со старыми контрольными суммами и две видимые проекции во всех пяти запусках. Контрольная сумма входного файла слота не менялась. Сопоставление отпечатков выполнено на диске. Клиент 0.1.2 проверял восстановление проекций и каталог библиотеки.

```text
same        blueprints=1 blueprint=QA_A
rename      blueprints=1 blueprint=QA_A_renamed
remove      blueprints=0
substitute  blueprints=1 blueprint=QA_A
duplicate   blueprints=2 blueprint=QA_A blueprint=QA_A_renamed

plan=0 digest=989bf4d6edaede970ec5bfdef1978b6b
plan=1 digest=219900e0f0be81613279571dda0b2fbb
subsystems=1 views=2 visible=2
```

Поле `FBlueprintHeader::BlueprintName` заполняется именем файла и отсутствует в сериализованном заголовке. `UFGBlueprintDescriptor` открывает имя, `mID`, габариты, цену, оформление и доступность рецептов. SDK выдаёт новый `mID` при создании дескриптора. Описание заголовка и эксперимент показывают, что габариты, цена, рецепты и таблица акторов могут совпасть для разных источников. Переименование пары файлов сохраняет все байты `.sbp`, поэтому при единственном совпадении можно использовать дескриптор с новым именем. [Заголовок и дескриптор SDK][types] · [API библиотеки SDK][library]

## Правило для B02

1. В Shipping CL 520140 вызовы идут от `AFGBlueprintHologram::BeginPlay` через `LoadBlueprintToOtherWorld`, `LoadStoredBlueprint` и `ReadBlueprintFromDisc` к `LoadFileFromDisk`. Этот путь проверен по вызовам в DLL. В пределах штатной загрузки голограммы зафиксировать BLAKE3 байтов успешного чтения `.sbp` для её дескриптора. Привязать результат к экземпляру preview. При F7 записать в `FShadowPlacement` сохраняемую строку `blake3-sbp-v1:<64 шестнадцатеричных символа>`. Если штатное чтение не удалось подтвердить, оставить поле пустым. Повторное чтение по имени во время F7 могло бы связать ещё открытый preview A с подменённым файлом B.
2. При каждом запросе строительства заново проверить `.sbp` в библиотеке текущего мира. Требуется ровно один совпадающий отпечаток с доступным штатным дескриптором. При нескольких совпадениях вернуть неоднозначность. При отсутствии совпадения сообщить об изменении, если прежнее имя занято, или об отсутствии, если файла больше нет. Если подходящий файл нечитаем, не удаётся получить дескриптор или формат отпечатка неизвестен, вернуть отказ с причиной. Перед применением проверенного источника следует сверить отпечаток фактически открытого игрового preview, а перед штатным подтверждением снова проверить источник, поскольку `Construct` вызывает загрузку по имени.
3. Для старой записи пустое поле означает, что восстановить идентичность источника нельзя. Два файла A и B уже показывают, почему снимок геометрии не даёт такой гарантии. Отказ влияет только на строительство. Сохранённые GUID, поза, геометрия, выбор и видимость проекта сохраняют прежнее поведение. Q01 нужно проверить пустое поле у старых записей и сохранение точной строки отпечатка у новых.

Изменение байтов при пересохранении будет считаться изменением источника, даже если сцена выглядит так же. Для клона с теми же байтами и новым именем происхождение файла восстановить невозможно. Решение о строительстве в этом случае опирается на совпадение полного содержимого.
