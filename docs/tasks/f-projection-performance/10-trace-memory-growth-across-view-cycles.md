# F10. Выяснить, почему растёт память при переключении видов

**Цель.** На сцене со 100 планами отделить рост RAM от самих переключений от роста за то же время в неподвижном мире. Определить, остаются ли живы компоненты старых проекций, какие выделения памяти сохраняются после выгрузки и выходит ли расход на плато.

**Исходные данные.** В F09 после пяти циклов частный рабочий набор вырос на 354–358 МиБ при обычной отрисовке и на 447–471 МиБ с ISM. После возвращения в пустой мир дополнительный остаток с ISM составил 119–152 МиБ относительно обычной отрисовки. Устойчивого штрафа по выделенной VRAM серия не выявила. Эти измерения процесса сами по себе не указывают владельца памяти. [Методика F09](09-measure-ism-memory.md) · [Сцена и экспериментальная сборка F08](08-benchmark-per-plan-instancing.md)

## Сценарий

Используйте одну копию экспериментального ZIP F08, одинаковые настройки, камеру и входные слоты. Сверьте SHA-256 архива и загруженной DLL. Запускайте в отдельных процессах четыре варианта:

| Отрисовка | Контроль времени | Переключения |
|---|---|---|
| Обычная | Стоять в Ghost на 100 планах | 30 циклов Ghost → Wireframe → Footprint → Ghost |
| ISM (`-ShadowPerPlanISM`) | Стоять в Ghost на тех же 100 планах | Те же 30 циклов |

1. Маршрут каждого процесса: главное меню → пустой слот `SAQ_F02_000_PILOT` → сетка `SAQ_F02_100_PILOT` → главное меню → тот же пустой слот. Используйте тестовые копии при закрытой пользовательской игре. Фиксируйте память после стабилизации. В контроле воспроизведите расписание, длительность, сбор метрик и движения между мирами из соответствующего прогона с переключениями. Чередуйте порядок вариантов. Сделайте минимум две независимые серии из четырёх запусков, чтобы сопоставить эффект с разбросом.
2. Начните с маршрута SaveCheck из F09, если он доступен в рабочей копии. Для чистого клона точки расширения — кадровый сборщик `ProjectionPerformanceCheck.cpp` и регистрация сценариев SaveCheck. Поддержите выбор маршрута и числа циклов параметрами тестового запуска. Версию мода, слоты и фактические интервалы запишите в протокол. [Сценарии проекций](../../../tests/compatibility/SaveCheck/Source/SaveCheck/Private/ProjectionPerformanceCheck.cpp) · [Условия запуска](../../background-testing.md)
3. Снимайте частный рабочий набор и private bytes одного PID в МиБ от первого меню до конца процесса. Для каждой точки сохраняйте метку времени, режим и номер цикла. Отдельно считайте живые акторы проекций, обычные mesh-компоненты и ISM-компоненты, число зарегистрированных компонентов и экземпляров ISM. Учтите также снятые с регистрации объекты старых представлений и предыдущего мира, которые ещё ожидают сборки мусора. Не держите сильные ссылки на них ради измерения.

## Независимая проверка

- [x] Во всех вариантах исходный Ghost содержит 100 планов и 3 800 визуальных деталей. В обычном режиме — 3 800 mesh-компонентов, в ISM — 600, из них 500 групп. Подтвердите 90 фактических смен вида в активном маршруте и ноль в контроле. При возврате в пустой слот зарегистрированных проекций сетки больше нет.
- [x] Для каждого возврата в Ghost и соответствующей временной точки контроля приведите прирост RAM от исходного Ghost. Покажите значения на циклах 0, 5, 10, 20 и 30. Сначала вычтите дрейф неподвижного мира для каждого режима, затем сравните полученные величины между обычной отрисовкой и ISM. Покажите прирост за последние десять циклов и разброс повторов, чтобы обосновать вывод о плато или продолжающемся росте.
- [x] Снимите число живых объектов и объём памяти по доступным категориям до переключений, в последнем Ghost, после выгрузки сетки **до и после завершения диагностической сборки мусора (GC)** и в повторно открытом пустом мире. Используйте одинаковые точки GC и ожидания во всех четырёх вариантах. Отличайте память занятых объектов от зарезервированных страниц аллокатора. Если Shipping не даёт разбивки, снимите её отдельным диагностическим прогоном и укажите границы сопоставимости. [Код смены вида](../../../src/ShadowArchitect/Source/ShadowArchitect/Private/ShadowPlan.cpp) · [Создание компонентов](../../../src/ShadowArchitect/Source/ShadowArchitect/Private/ShadowProjection.cpp)
- [x] Передайте команды запуска, хеши, CSV по прогонам и сводку по четырём вариантам. Если после GC сохраняются объекты прежнего представления, укажите их класс, количество и подтверждённый путь удержания хотя бы одного объекта. Если число объектов вернулось к исходному, покажите, какие категории памяти сохраняют избыток. Для неатрибутированного остатка укажите величину и следующий конкретный замер. Завершите выводом отдельно для обычной отрисовки и ISM. От него зависит, нужен ли эксперимент с исправлением перед включением ISM по умолчанию.

## Воспроизведение

Для запуска нужны изолированный клиент F08 с `hashes.json` из опыта F08, тестовая библиотека `Saved/F-projection-performance/Blueprints` и два слота из сценария. Соберите только модуль SaveCheck для `FactoryGameSteam Win64 Shipping` по исходникам этой задачи. Поместите плагин вместе с дескриптором и манифестом в `Saved/F10-memory/SaveCheck`. DLL ShadowArchitect берётся из экспериментального ZIP F08. Сборщик проверяет её SHA-256, SHA-256 ZIP и хеши входных слотов. Маршрут отключает автосохранение и проходит оба слота без записи. [Подготовка клиента и слотов](../../background-testing.md#f01-и-f02-время-и-память-проекций)

```text
python -B scripts/run_projection_memory_trace.py --pilot
python -B scripts/run_projection_memory_trace.py
python -B scripts/run_projection_memory_trace.py --diagnostic
python -B scripts/projection_memory_trace_report.py Saved/F10-memory --output docs/evidence
python -B scripts/projection_memory_trace_report.py Saved/F10-memory --diagnostic --output docs/evidence
```

- Оба маршрута используют `-SaveCheckProjectionMemory -SaveCheckMemoryCycles=30 -SaveCheckMemorySettle=0.9 -SaveCheckMemoryWindow=0.9`. Параметр `-SaveCheckMemoryRoute=cycle` отправляет Ctrl + Shift + G через игровой контроллер. Параметр `-SaveCheckMemoryRoute=idle` оставляет Ghost. SaveCheck принимает окно только после проверки позы, зарегистрированных компонентов, материала и числа деталей ожидаемого вида. Режим ISM включается `-ShadowPerPlanISM`.
- Окна сетки привязаны к одному расписанию с шагом 1,8 с от первого Ghost. Перед окнами нового мира и после диагностического GC отводится не менее 3 с. После окна меню отрабатывают полный GC и барьер очереди рендера. Память снимается с частотой 5 Гц по PID настоящего процесса игры. Для сравнений используется медиана каждого окна. QPC в CSV соответствует монотонным часам SaveCheck.
- SaveCheck сверяет зарегистрированные компоненты в каждом окне. Для контрольных снимков он обходит массив UObject, включая объекты в процессе очистки. `current` содержит живые проекции текущего мира, `removed` — снятые с регистрации и ожидающие удаления объекты текущего мира, `previous` — проекции за его пределами. `object_bytes` учитывает размер экземпляров UObject и ёмкость массива трансформаций ISM. Ссылки для удержания объектов при этом не создаются.
- В диагностическом повторе SaveCheck также пишет общий и сразу освобождаемый объёмы кэша страниц Binned2. `VirtualQueryEx` измеряет объём областей `MEM_COMMIT` по типам `MEM_PRIVATE`, `MEM_MAPPED`, `MEM_IMAGE` и отдельно `MEM_RESERVE`. Эти счётчики описывают виртуальные страницы. В закоммиченных областях могут одновременно находиться живые выделения и свободные блоки Binned2. Для copy-on-write областей Windows сохраняет исходный тип отображения, поэтому частные страницы PSAPI и `MEM_PRIVATE` сопоставляются как разные измерения. [Документация VirtualQueryEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualqueryex) · [Состояния страниц Windows](https://learn.microsoft.com/en-us/windows/desktop/Memory/page-state)

### Рост на сетке

К 30-му циклу частный рабочий набор вырос относительно первого Ghost на **580–590 МиБ в обычных циклах** и **725–728 МиБ в циклах ISM**. При неподвижном Ghost за то же время рост составил **445–449 МиБ без ISM** и **721–722 МиБ с ISM**. Для private bytes те же четыре диапазона составили 430, 664–689, 344–353 и 642–676 МиБ соответственно.

После вычитания контроля вклад переключений в частный рабочий набор составил по циклам 0, 5, 10, 20 и 30:

- Обычная отрисовка — 0, +45…+66, +109…+111, +121…+128 и **+135…+141 МиБ**.
- ISM — 0, +5…+12, +11…+20, +12…+18 и **+4…+6 МиБ**.

Для private bytes на тех же циклах обычная отрисовка дала 0, −25…+9, +54…+59, +61…+72 и **+77…+86 МиБ**, ISM дал 0, +24…+34, +27…+31, +27…+29 и **+14…+23 МиБ**. К 30-му циклу ISM уменьшил вклад переключений относительно обычной отрисовки на 131–135 МиБ рабочего набора и на 63 МиБ private bytes в обеих сериях. [Все циклы, оба повтора и разности](../../evidence/F10-comparisons.csv)

За последние десять циклов вклад переключений без ISM вырос ещё на 13–14 МиБ рабочего набора и на 14–16 МиБ private bytes. С ISM он снизился на 6–14 и 6–13 МиБ соответственно. Прирост от переключений замедлился в обычном режиме и к 30-му циклу перестал расти с ISM. Совокупная память продолжала расти даже в неподвижном Ghost. Между 20-м и 30-м циклами рабочий набор контроля прибавил 173 МиБ без ISM и 262 МиБ с ISM.

### Выгрузка сетки

Перед выгрузкой в активном маршруте оба повтора показали **31 200** снятых с регистрации `UStaticMeshComponent` без ISM. С ISM осталось **1 600** `UStaticMeshComponent` и **4 000** `UInstancedStaticMeshComponent` с 29 600 экземплярами в массивах. Все эти объекты ожидали GC. Оценка их размеров по экземплярам UObject и массивам ISM составила 47,1 МиБ и 15,7 МиБ соответственно. В контролях число снятых с регистрации компонентов оставалось нулевым. В первом окне меню, после диагностического GC и в повторно открытом пустом мире во всех вариантах зарегистрированных, снятых с регистрации и ожидающих GC проекций оказалось **ноль**. ## Диагностический повтор

В Shipping Binned2 вернул `counters=0` для общего объёма живых выделений и объёма полученных от ОС страниц. Для дополнительного повтора собран SaveCheck с двумя доступными счётчиками свободного кэша Binned2, SHA-256 `77C32F0909A8A8C7AC7FA913CAB7EE00E96134FC0992A9388852DD66EA491FD3`. В четырёх дополнительных процессах использовались прежние ZIP, DLL мода, сценарии и интервалы. Получено 4 096 отсчётов, 384 окна и 28 снимков адресного пространства. Расхождение середины парных окон сетки составило до 83 мс. В этом повторе измерялись категории страниц и свободный кэш. Разброс эффекта переключений оценён по двум основным сериям. [Команды диагностических запусков и хеши](../../evidence/F10-diagnostic-launches.json) · [Отсчёты](../../evidence/F10-diagnostic-timeseries.csv) · [Окна](../../evidence/F10-diagnostic-windows.csv)

- В последнем Ghost объём частных закоммиченных областей вырос относительно первого Ghost на 361 и 288 МиБ в обычных циклах и контроле, на 683 и 545 МиБ в циклах и контроле ISM. В меню после выгрузки он был выше исходного меню на 1 039–1 296 МиБ до диагностического GC и на 1 079–1 342 МиБ после него. Нулевые счётчики проекций воспроизвелись в обоих окнах меню и в пустом мире. [Области Windows](../../evidence/F10-diagnostic-regions.csv) · [Снимки проекций и аллокатора](../../evidence/F10-diagnostic-views.csv)
- После возврата в пустой слот частные закоммиченные области оставались больше начальных на **622 МиБ в обычных циклах и 437 МиБ в обычном контроле**, на **820 МиБ в циклах ISM и 836 МиБ в контроле ISM**. Зарезервированное без commit адресное пространство изменилось от −21 до +24 МиБ. Отображения файлов и образов изменились менее чем на 1 МиБ. - Свободный кэш страниц Binned2 в повторно открытом пустом мире занимал 4–14 МиБ. В сравнении с исходным пустым миром он изменился на −4,9 и +2,3 МиБ в обычных циклах и контроле, на +4,8 и −2,2 МиБ в циклах и контроле ISM. Положительная добавка этого кэша составила менее 5 МиБ. Вклад переключений в остаток частного рабочего набора снова составил +79 МиБ без ISM и −32 МиБ с ISM. [Сравнения диагностического повтора](../../evidence/F10-diagnostic-comparisons.csv) · [Снимки свободного кэша](../../evidence/F10-diagnostic-views.csv)

Остаток по счётчику private bytes в диагностическом повторе составил **431–532 МиБ без ISM и 722–728 МиБ с ISM**. Класс страниц установлен, владельцы основной части остатка в этих измерениях не определены. Следующий замер — собрать отдельный Development-клиент с Memory Insights и счётчиками Binned2 `TotalAllocated` и `TotalOSAllocated`, запустить те же активный и контрольный маршруты с `-trace=default,memory` с начала процесса. Сравнить `Growth Vs Decline` между первым и 30-м Ghost и между двумя окнами пустого слота с группировкой по стеку и тегу. Разность счётчиков Binned2 покажет накладные расходы страниц, а Memory Insights — живые выделения по владельцам. [Запись и запросы Unreal Memory Insights](https://dev.epicgames.com/documentation/unreal-engine/memory-insights-in-unreal-engine)

## Решение

- **Обычная отрисовка.** После вычитания контроля остаётся воспроизводимый рост от переключений. В последних десяти циклах он замедляется и продолжается. Объекты старых видов освобождаются при выгрузке, но частный рабочий набор после возврата остаётся на 67–84 МиБ выше контроля.
- **ISM.** Вклад переключений к 30-му циклу мал и в последних десяти циклах уменьшается. Больший общий расход воспроизводится уже в неподвижном Ghost, в том числе после возврата в пустой мир. Оставить `-ShadowPerPlanISM` экспериментальным. Перед включением по умолчанию локализовать источники этого остатка и проверить исправление на паре с неподвижным Ghost и на полном маршруте из 30 циклов.
