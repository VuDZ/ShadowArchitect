# F05. Завершить контрольные замеры F01 и F02

**Цель.** Установить, при каком числе видимых модулей появляется заметная задержка, и отделить влияние диагностики от стоимости переключения и постоянной отрисовки. Используйте слоты, генератор и CSV из исходного [пилота F02](02-benchmark-large-layouts.md). Результаты этой серии закроют соответствующие пункты [F01](01-measure-projection-cost.md) и F02 без второго прогона тех же сценариев.

## Независимая проверка

- [x] Снимите матрицу 0, 10, 25, 50 и 100 экземпляров одного Blueprint на исходной реализации. Сохраните кадр, подтверждающий видимость всей сетки 10×10. Используйте ту же камеру для остальных размеров. Если камеру пришлось сдвинуть, переснимите пустой контроль. Для каждого размера выполните не менее трёх новых процессов с повторной загрузкой слота и полными циклами видов. Разделите первый и прогретый циклы. Используйте равные окна устойчивого состояния, для сравнения с пилотом укажите длительность.
- [x] На 2 и 100 планах сделайте парные повторы с `-ShadowProjectionProfile` и без него. Сохраните общий кадровый сборщик в обоих случаях. Привяжите кадр выполнения операции к номеру кадра или метке обработанного действия. Отдельно сравните этот кадр и максимум следующих пяти. В контроле без профилировщика используйте независимую метку ввода и явно укажите точность привязки. Так можно проверить, повторяется ли задержка, увиденная на двух планах через два кадра после вызова.
- [x] Приведите по режимам время кадра p50/p95, FPS, draw calls, число компонентов, а для восстановления и переходов — время операции и изменение памяти процесса по методике F01. Для устойчивых Ghost и Footprint хотя бы на 0 и 100 планах приложите раздельные замеры времени GPU и потока отрисовки с указанием инструмента. Если Shipping не выдаёт эти счётчики, зафиксируйте ограничение и снимите их доступным инструментом на сопоставимой сборке, пометив результаты отдельно. Одни draw calls не позволяют определить узкое место.
- [x] Для худшего перехода сохраните покадровый участок до, во время и после вызова с отметками фаз. Укажите разброс между процессами и подтвердите сохранность GUID, поз и числа компонентов после циклов. Перенесите результаты в карточки F01/F02, отмечая только фактически проверенные критерии. [Запуск SaveCheck и формат данных](../../background-testing.md#f01-и-f02-время-и-память-проекций)

В выводе дайте два отдельных решения. Для паузы Ghost → Wireframe передайте контрольные цифры в [F03](03-reuse-components-for-wireframe.md). Для постоянно видимых планов укажите, оправдывают ли замеры эксперимент с объединением одинаковых мешей через ISM/HISM. Если измерения не разделяют стоимость GPU и потока отрисовки, сохраните этот вопрос открытым.

## Условия контрольной серии

24 ноября 2026 года. Satisfactory Steam 1.2.5.1 CL `520140` (`rel-main-1.2.6`), SML `3.12.1`, Shadow Architect 0.3.0. Исходная реализация `f3c08e0`, SHA-256 DLL `18afc819f44b75521e6749cfddd7cd4fcedc8bbbc59e029d0468fb311d1ef51d`. SaveCheck из `e6ec66d` с измерителями F05. Ryzen 7 9800X3D, RTX 5080, D3D12, 1280×720, внеэкранный рендеринг. VSync, лимит FPS и фоновая пауза отключены.

Слоты на базе `SAQ_H01_SUPPORT_02` по возрастанию числа планов: `SAQ_F02_000_PILOT`, `SAQ_F05_010`, `SAQ_F05_025`, `SAQ_F05_050`, `SAQ_F02_100_PILOT`. Для пар на двух планах использован `SAQ_BASE_01`. Выходные слоты создавались только при подготовке сеток. Измерительные прогоны выполнялись с отдельными каталогами, автосохранение выключено. Временные окна устойчивых видов по 3 с совпадают с пилотом. Камера, Blueprint и шаг сетки из F02. [Подготовка сцены](02-benchmark-large-layouts.md#пилот-на-100-размещениях)

В калибровочном кадре видна вся сетка. SaveCheck проецирует восемь углов общих габаритов каждого плана и подтверждает `grid_in_frame=100 total=100`. Прямоугольник всех планов занимает от `(325, 198)` до `(978, 699)` пикселей кадра 1280×720. [Кадр Ghost](../../evidence/F05-grid-100.png)

Время кадра — интервал между окончаниями кадров. FPS — число кадров за фактическую длительность окна. Draw calls и время GPU сняты через RHI для GPU 0. Время потока отрисовки снято через `GRenderThreadTime`. Берётся последний доступный отсчёт потока отрисовки. Эти два счётчика описывают перекрывающуюся работу. Commit charge — `FPlatformMemory::GetStats().UsedVirtual` в МиБ. Снимки фазы операции дополняет отдельная выборка на кадрах примерно каждые 100 мс. Пик в этих данных означает максимум зарегистрированных выборок в пределах операции. Во всех циклах SaveCheck нажимал Ctrl+Shift+G.

## Результат 21 запуска

Матрица включает по три новых процесса на размер и повторную загрузку того же слота внутри каждого процесса. На 100 планах выполнено по два цикла до и после перезагрузки. Для 2 и 100 планов есть по две пары процессов с включённой и выключенной диагностикой. Все запуски дали `pass=1`. SaveCheck сверил GUID, позы и число компонентов в циклах и после перезагрузки. SHA-256 всех шести входных слотов сохранились. CSV хранит каждый процесс, первое открытие (`run=0`), повторную загрузку (`run=1`) и каждый устойчивый вид. Пустые поля операций относятся к выключенной диагностике или восстановлению до начала кадровой выборки. Кадр восстановления при повторной загрузке включает смену мира. [Окна FPS, p50/p95, GPU, поток отрисовки и компоненты](../../evidence/F05-windows.csv) · [Операции, память и кадры](../../evidence/F05-operations.csv)

Первый кадр Ghost → Wireframe дал медианы **4,45 / 8,95 / 17,03 / 32,10 / 50,07 мс** при 0 / 10 / 25 / 50 / 100 планах. При 25 планах диапазон 16,58–22,89 мс находится около бюджета кадра 16,67 мс для 60 FPS. На 50 планах диапазон 31,82–32,45 мс превышает этот бюджет во всех первых циклах. На 100 планах совокупный диапазон с прогретыми циклами 43,54–69,37 мс. Переключение с диагностикой давало 3 800 → 7 600 → 3 800 компонентов и 9,72–11,46 МиБ наблюдаемого пика commit charge сверх значения перед вызовом.

На 50 планах разрешение мешей занимало 0,041–0,045 мс, регистрация входящих компонентов — 6,55–7,46 мс. На 100 планах соответственно 0,076–0,085 мс и 10,70–14,94 мс. Все ссылки разрешались в загруженные объекты перед вызовом. Худший переход прошёл в кадре 6166 прогона `F05-100-r3-on`: 63,49 мс на игровом потоке, 69,37 мс целого кадра, 13,28 мс максимум следующих пяти. Подготовка и очистка наборов видны по `before`, `coexist`, `after`. [Покадровый участок](../../evidence/F05-worst-transition.csv)

Для всех 120 переключений с диагностикой метка ввода плюс один кадр точно совпала с номером кадра вызова. Серия без диагностики использует эту оценку с точностью до одного кадра, подтверждённой включёнными прогонами. На двух планах Ghost → Wireframe с диагностикой поднял кадр вызова на 0,56–5,29 мс относительно пары, медиана +2,31 мс. Ранее наблюдавшиеся 60 мс через два кадра не повторились, максимум следующих пяти кадров в этой серии 10,96 мс. На 100 планах медиана парной разницы −0,30 мс, диапазон от −22,64 до +3,10 мс. Без диагностики переход всё равно занял 44,53–69,23 мс. Максимум следующих пяти кадров без диагностики составил 17,76 мс.

- **F03.** Основной пик приходится на кадр команды, с ростом числа создаваемых и уничтожаемых компонентов. Сравниваем переиспользование тех же мешей по кадру вызова, следующим пяти кадрам и пиковому числу компонентов. [Эксперимент F03](03-reuse-components-for-wireframe.md)
- **Устойчивая отрисовка.** Для Ghost медиана первого устойчивого окна выросла с 4,56 до 6,75 мс (p95 с 4,86 до 8,65 мс), draw calls с 2 946 до 10 180. Время потока отрисовки выросло с 1,82 до 4,83 мс, GPU с 4,25 до 4,45 мс. Для Footprint на 0 и 100 планах поток отрисовки дал 1,78 и 1,71 мс, GPU — 4,26 и 4,28 мс. Рост работы потока отрисовки при 100 планах оправдывает эксперимент с ISM/HISM для повторяющихся совместимых мешей и материалов, с повтором тех же счётчиков на сетке F05.
